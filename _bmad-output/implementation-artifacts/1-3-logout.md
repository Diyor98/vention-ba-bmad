# Story 1.3: Logout

Status: review

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a **logged-in user (Guest or Super Admin)**,
I want **to log out from a header button on any page**,
so that **my session ends and I return to the public landing page.**

> Verbatim from Document B §8 (US-1.3). FR-A3 (logout terminates the session). **This story also introduces the global header chrome** (a deliberate architectural addition reserved for US-1.3 by both US-1.1 and US-1.2 — see those stories' anti-pattern lists).

## Acceptance Criteria

Verbatim Gherkin from Document B §8 US-1.3, lifted as one numbered AC, plus implementation-shaped ACs:

1. **AC-1 (Logout flow).**
   ```gherkin
   Given I am logged in as a Guest
   When I click "Log out"
   Then my session is terminated
   And I am redirected to "/"
   And I see "Log in" and "Register" links in the header
   ```

2. **AC-2 (Authenticated header content).** When a session exists, the header shows the user's identifier (email is sufficient — no profile screen exists per Doc B §7.2's screen-inventory closure) and a "Log out" button. The "Log in" and "Register" links are NOT shown.

3. **AC-3 (Unauthenticated header content).** When no session exists, the header shows "Log in" (linking to `/login`) and "Register" (linking to `/register`). No user identifier is shown. No "Log out" button is shown.

4. **AC-4 (Header on every page).** The header is rendered by the root layout, so it appears on `/`, `/register`, `/login`, and every future page added in Epics 2-4. It is not a `(public)/layout.tsx` group layout — it is genuinely global, because every page (public or authenticated) needs to display either the auth links or the logout button.

5. **AC-5 (Brand link).** The header includes "DeskHive" on the left as a link to `/`. The `/` route loads the public landing page (currently the create-next-app welcome page; replaced in US-3.1).

6. **AC-6 (Server Action pattern).** Logout uses the architecture's Server Action pattern:
   - The "Log out" button is a `<form action={logoutAction}>` submit button.
   - `logoutAction` calls `auth.api.signOut({ headers: await headers() })` and then `redirect('/')` — placed AFTER the try/catch (same redirect-signal-preserving rule as US-1.1's `registerAction`).
   - The button shows the disabled-on-submit state via `useFormStatus().pending`, with label "Signing out…" while pending. (Doc B §7.5 cross-cutting rule.)

7. **AC-7 (REST wrapper).** A `POST /auth/logout` REST handler exists at `src/app/api/auth/logout/route.ts` for Doc B §6.4 compliance. It calls `auth.api.signOut({ headers: req.headers })`, returns 200 with `{ success: true }` on success, and uses `apiError`/standard helpers on failure.

8. **AC-8 (Anti-enumeration / always-succeed semantics).** Logout is idempotent — calling it without a session, with an expired session, or with a corrupted cookie all produce the same outcome: any session cookie is cleared and the user is redirected to `/`. **Logout never shows an error message to the user**, even if `auth.api.signOut` rejects internally (the catch swallows the error and proceeds to `redirect('/')`). This matches the architecture's principle of session-state-flush-on-best-effort.

9. **AC-9 (Session-read pattern established).** The header uses `await auth.api.getSession({ headers: await headers() })` in a Server Component to read the current session. This is the **first introduction of the session-read pattern**; all future authenticated UI (My Bookings, Admin pages) will replicate it. (architecture §Authentication & Security; architecture §Frontend Architecture.)

10. **AC-10 (Dynamic rendering acknowledged).** Adding a `headers()` call to the root layout opts every route into dynamic rendering. After this story, `/`, `/register`, and `/login` are no longer statically prerendered — they are server-rendered on demand. **This is expected and not a regression.** The `pnpm build` output should show all three as dynamic (`ƒ`) instead of static (`○`).

11. **AC-11 (Page metadata).** The root layout's `metadata.title` is updated from `"Create Next App"` to `"DeskHive"`, and `metadata.description` from `"Generated by create next app"` to a brief project description. (Small polish, naturally bundled with this story since the layout is being modified.)

12. **AC-12 (Single commit).** All US-1.3 changes land in a single commit on `main` titled exactly `feat: logout button and global header (US-1.3)`. Commit content is only files under `deskhive/`.

## Dev Notes

### What gets built and what's deliberately out of scope

This is the **third (and final) story of Epic 1 — Authentication**. After it lands, the full auth loop is closed: register → login → logout → re-login. Epic 1 is complete and ready for retrospective.

This story also **establishes two patterns that all future Epic 2-4 stories will inherit:**
1. **Global header chrome** — every page renders inside the same root layout that includes `<Header />`. Future stories should NOT re-wrap their pages with their own headers; they consume the global one.
2. **Server-side session read** — `await auth.api.getSession({ headers: await headers() })` is the canonical way to read the current session from a Server Component. This is the foundation for `requireSession()` / `requireRole()` (introduced in Epic 2) and for any "if logged in, show X" UI.

Feature scope (US-1.3 only):
- ✅ Global header in the root layout
- ✅ Conditional header content based on session state
- ✅ Logout Server Action + button
- ✅ REST wrapper at `POST /auth/logout`
- ✅ Layout metadata updated to "DeskHive" branding

Out of scope for US-1.3 (do NOT build):
- ❌ A profile page or user dropdown menu (Doc B §7.2 closes the screen inventory)
- ❌ "Are you sure you want to log out?" confirmation modal
- ❌ Multi-device logout / "log out from all sessions" (Phase 2)
- ❌ Session timeout / idle-warning UI (Phase 2)
- ❌ Custom 404 / 500 / error UI improvements (separate story if ever needed)

- ❌ Switching from email/password to OAuth providers (Phase 2)

- ❌ A `(public)/layout.tsx` group layout — header is genuinely global, no group-level chrome needed.

### Key architectural decisions (non-negotiable unless escalated)

- **Header in root layout, not in pages.** The header is global. Putting it in pages would force every new page to remember to include it.
- **Server Component header (not Client).** The architecture's pattern is server-side session reads. A Client Component header using Better Auth's `useSession()` hook would (a) cause a client-server hydration jitter, (b) require an extra API roundtrip, and (c) split the auth-state source of truth across the client/server boundary. Keep it server-side.
- **`<form action={logoutAction}>` (not `<button onClick>`).** Server Actions require form-based submission to participate in Next.js's progressive-enhancement story (works without JS). This also gets us automatic CSRF protection and the `useFormStatus` pending state for free.
- **Logout always-succeeds semantics.** If `auth.api.signOut` throws (e.g., network issue against the session store), we still redirect — the user's session cookie either gets cleared by Better Auth's response handling or we accept it as already-stale and redirect anyway. **Never show the user a "logout failed" error.**
- **Header's `await headers()` opts every route into dynamic rendering.** This is intentional and architecturally fine for a Phase 1 MVP — Next.js dynamic rendering is fast (the build output already shows API routes at `ƒ` with no perf issue). When Phase 2 wants caching back, it can use Partial Prerendering (PPR) or split the static landing into a sub-tree without the header. Out of scope for now.
- **No client-side auth state (no React Context for user, no Zustand store).** Each page reads its own session via `getSession()` if it needs it. Avoids stale-state bugs.

### Architecture compliance

- **Validation:** N/A for logout (no input).
- **Form pattern:** Native `<form action={serverAction}>` + `useFormStatus`. **NO React Hook Form, Formik, etc.**
- **State management:** None client-side. Server-side session is the source of truth.
- **Component library:** None. Raw Tailwind utility classes only.
- **Error response shape (server):** `{ status: 'error', code, message }` (Server Action) — but logout has no user-facing error path; this shape is for future stories.
- **Status codes (REST wrapper):** 200 on success, 500 on internal error.
- **Auth:** Better Auth's `auth.api.signOut` and `auth.api.getSession` are the only paths — never raw cookie manipulation.
- **Reskinnable frontend:** All visible classes are literal Tailwind utilities; no design tokens in TS.

### logoutAction — extension to `src/actions/auth.ts`

```ts
// Append to existing file.

import { headers } from 'next/headers';

export async function logoutAction(): Promise<void> {
  try {
    await auth.api.signOut({ headers: await headers() });
  } catch (err) {
    // Swallow — AC-8 says logout is best-effort. Log for debuggability.
    const msg = err instanceof Error ? err.message : String(err);
    logger.error('logout_action_failed', { error: msg });
  }
  redirect('/');
}
```

**Note:** `logoutAction` is `Promise<void>` — no `useActionState`-shaped return value because the user never sees a logout error. The `redirect('/')` always runs (or throws the redirect signal, which is what we want).

### Header Server Component

```tsx
              Log in
            </Link>
            <Link href="/register" className="text-gray-700 hover:underline">
              Register
            </Link>
          </>
        )}
      </nav>
    </header>
  );
}
```

### POST /auth/logout — REST wrapper

Path: `deskhive/src/app/api/auth/logout/route.ts`

```ts
import { auth } from '@/lib/auth/config';
import { apiError } from '@/lib/http';
import { logger } from '@/lib/logger';

export async function POST(req: Request): Promise<Response> {
  try {
    await auth.api.signOut({ headers: req.headers });
    return Response.json({ success: true }, { status: 200 });
  } catch (err) {
    const msg = err instanceof Error ? err.message : String(err);
    logger.error('logout_route_failed', { error: msg });
    return apiError('INTERNAL_ERROR', 'Something went wrong', 500);
  }
}
```

This wrapper exists for Doc B §6.4 contract compliance. The page does NOT consume it; the LogoutButton calls the Server Action directly. **The session cookie clearing happens inside `auth.api.signOut` and is propagated via Better Auth's response context** — when called from a Route Handler with the standard request headers, Better Auth's adapter sets the appropriate `Set-Cookie` headers in the eventual Response (handled by `auth.api.signOut`'s side effects).

If clients of this REST endpoint observe that the session cookie isn't cleared, switch to `auth.api.signOut({ headers: req.headers, asResponse: true })` and forward the returned Response directly. Document the choice in Completion Notes.

### Anti-patterns — explicit DO-NOTs

- ❌ Using Better Auth's `useSession()` client hook in the Header. Server-side reads only.
- ❌ Adding a "Profile" or "Settings" link in the header. No such screens exist in §7.2.
- ❌ Adding a "Confirm log out" modal.
- ❌ Adding `requireSession()` or `requireRole()` to the Header's logic. The Header reads optional session — it's not authorization enforcement.
- ❌ Calling `cookies()` directly to read the session. Use `auth.api.getSession({ headers: await headers() })`.
- ❌ Storing user state in a React Context, Zustand store, or Redux. The Header re-reads on every render (which is once per server-rendered request). No client-side cache.
- ❌ Showing a "logout failed" error message to the user. Logout always-succeeds (AC-8).
- ❌ Adding a `(public)/layout.tsx` route-group layout. Header is global, not public-only.
- ❌ Modifying `src/app/page.tsx` (welcome page; smoke test depends on it).
- ❌ Adding `<Header />` inside individual pages. It belongs in the root layout.
- ❌ Caching the Server Component Header with `unstable_cache` or `revalidate`. Session reads MUST be dynamic.
- ❌ Hardcoding the redirect target as `'http://localhost:3000/'`. Use `redirect('/')`.
- ❌ Catching `redirect()` inside `try`/`catch`. (Same redirect-after-try-catch rule as US-1.1.)

### Project structure notes

- `src/components/header.tsx` is a Server Component. Even though Server Components and Client Components can be co-located in the same folder, for readability:
  - `header.tsx` (Server) reads session, renders structure.
  - `logout-button.tsx` (Client) handles the form interaction with `useFormStatus`.
  - This split is the standard "RSC composition" pattern: server fetches data, client handles interactivity.
- `src/lib/auth/guards.ts` (the architecture's planned `requireSession` / `requireRole` / `requireOwnership`) is **STILL not introduced in this story**. The header reads session optionally; guards are for routes that *demand* a session. First demand is in Epic 2's US-2.1.

### Completion Notes List

**Story executed end-to-end. Stop bar (header renders globally; click "Log in" or "Register" works) achieved.** All 53 unit tests + 8 E2E tests pass. Epic 1 is now structurally complete; only manual verification remains before BA review.

**Key implementation observations:**

1. **Smoke test updated alongside metadata.** The US-0.3 smoke test asserted `await expect(page).toHaveTitle(/Create Next App/)` — the create-next-app default. AC-11 changed the title to `"DeskHive"`, so the smoke test had to follow. Updated to `await expect(page).toHaveTitle(/DeskHive/)` and renamed to `home page renders with DeskHive title`. **This was not in the story's planned File List but was a required follow-on** — the alternative was reverting AC-11, which would have left "Create Next App" branding visible in production tabs. Smoke test is now correctly aligned with the new title; the welcome-page H1 / content (also "create-next-app"-themed) remains unchanged per the anti-pattern (US-3.1 replaces it).

2. **Better Auth session shape.** `auth.api.getSession({ headers })` returns either `null` (no session) or `{ user, session }` where `user` includes `email`, `name` (mapped to `fullName` per US-0.2 follow-up), `role`, and Better Auth's standard fields. Access path used: `session?.user?.email`. No version-skew workaround needed.

3. **All routes dynamic — confirmed.** Build output shows ALL routes as `ƒ` (dynamic, server-rendered on demand). Previously `/`, `/login`, `/register` were `○` (static). This is the expected consequence of `await headers()` in the root layout. Performance impact is acceptable for Phase 1 MVP; PPR (Partial Prerendering) is the optimization tool if it ever becomes a concern.

4. **No `useActionState` for logout.** Logout has no error path the user sees (AC-8). The form is `<form action={logoutAction}>` directly, which Next.js handles transparently. `useFormStatus` is still used inside the SubmitButton for the disable-on-submit state (AC-6).

5. **Header E2E tests use scoped `<header>` locators.** Tests assert against `page.locator('header').getByRole('link', { name: ... })` rather than page-wide selectors, avoiding collisions with any future "Log in" link that may appear inside page bodies (e.g., a CTA on the welcome page in US-3.1).

6. **Header is the first introduction of the session-read pattern.** This pattern (`await auth.api.getSession({ headers: await headers() })` in a Server Component) is what Epic 2/4's `requireSession` / `requireRole` guards will wrap. No abstraction yet — the Header reads session optionally and conditionally renders. The first DEMAND-a-session route lands in Epic 2's US-2.1.

7. **No changes to `src/lib/auth/config.ts`.** Both `signOut` and `getSession` are enabled by `emailAndPassword.enabled = true` (set in US-0.2). No new config keys.

8. **Three E2E tests for the unauthenticated header.** The authenticated header (logout flow) is DB-dependent and not in CI's E2E job (no Postgres service container yet). Manual verification (Task 8) covers it.
