1. Контекст
Махбуба, привет! Спасибо за дизайн Phase 1 — он отлично сел в продакшен. Эпики 5-1 и 5-2 успешно интегрированы, дизайн-система работает. Теперь начинаем Phase 2 — большой следующий шаг для DeskHive.
Phase 2 превращает DeskHive из одно-арендаторской платформы (где все пространствами управляет один Super Admin) в полноценный маркетплейс по модели Airbnb. Теперь у нас будут независимые владельцы пространств (Space Owners), реальные платежи через Stripe и email-уведомления.
2. Изменение модели пользователей
В Phase 1 у нас были две роли: Guest (бронирует столы) и Super Admin (управляет всем). Это упрощение.
В Phase 2 — три роли по модели Airbnb:
Guest — все регистрируются именно так. Может бронировать столы, оплачивать, отменять.
Space Owner (хост) — Guest, который подал заявку и был одобрен Super Admin&apos;ом. Может создавать свои пространства, управлять бронированиями, получать выплаты. Важно: Space Owner остаётся и Guest&apos;ом — может бронировать столы на других пространствах.
Super Admin — внутренний оператор DeskHive (мы с тобой и команда Vention). Одобряет заявки на хостинг, разбирает споры. Не владеет пространствами сам.
Ключевой принцип Airbnb: один логин для всех. Без переключателя Guest/Admin на странице логина. После входа Space Owner может переключаться между режимом Guest (бронирую) и режимом Host (управляю) через выпадающее меню в шапке — мы это уже реализовали в коде (Story 7-1).
3. Три темы Phase 2
Phase 2 разбита на три темы. Они идут параллельно с зависимостью: Theme A ставится первой, Themes B и C — после неё.
Theme A — Multi-Tenant (Space Owner)
Поток превращения Guest&apos;а в Space Owner: заявка → рассмотрение Super Admin&apos;ом → одобрение/отклонение → email-уведомление → доступ к панели хоста. Плюс панель управления для Space Owner: дашборд, мои пространства, бронирования, настройки выплат.
Theme B — Платежи через Stripe
Реальная оплата при бронировании (Stripe Checkout). Удержание средств при заявке, списание после подтверждения хостом, возврат при отмене. Хосты проходят онбординг Stripe Connect Express. Комиссия платформы — 15% (рабочее значение). Вся Phase 2 строится против Stripe test mode — реальных платежей не будет.
Theme C — Email-уведомления
Транзакционные письма на каждое значимое событие: подача заявки, одобрение/отклонение, новое бронирование, подтверждение оплаты, возврат средств, выплата хосту. Провайдер — Resend. Дизайн email-шаблонов также входит в твою работу — нужна базовая HTML-шапка/футер в фирменном стиле + 13 типов писем.

5. Дизайн-ограничения
Продолжаем дизайн-язык Phase 1 (индиго-бренд, нейтральные оттенки, Inter typography, карточная вёрстка). Новых цветов не вводим, новых типографических шкал не добавляем.
StatusBadge — Используем существующий компонент для всех статусов. Понадобятся новые варианты: PENDING / APPROVED / REJECTED для заявок.
Toast (всплывающие уведомления) — Используем существующий обёртку src/lib/toast.ts (Story 6-3). Тон сообщений и стиль уже зафиксированы.
Десктоп-приоритет. Мобильная адаптивность желательна, но не обязательна на Phase 2.
Никаких новых внешних библиотек — компонентов или иконочных сетов без согласования.
6. Тон и копирайт
Тон Phase 1 уже зафиксирован — спокойный, дружелюбный, без маркетинговой пафосности. Примеры из Story 6-3 (toast после бронирования):
  • &quot;Booking requested&quot; + &quot;We&apos;ll let you know when it&apos;s confirmed.&quot;
  • &quot;Booking cancelled.&quot;
Email-уведомления должны звучать в том же тоне. Например: &quot;Your booking request was received. We&apos;ll email you when the space owner confirms.&quot; — это естественное продолжение голоса toast&apos;а.
7. Что в Phase 2 НЕ входит
Чтобы не путать — следующие фичи отложены на Phase 3 или дальше:
Отзывы и рейтинги (guest → owner, guest → space)
Многодневные бронирования (всё ещё по одному дню)
Фотогалереи пространств (по-прежнему одно главное фото)
Иконки удобств (Wi-Fi, кофе и т.д.)
Мобильное нативное приложение
Корпоративные / командные аккаунты
Мультивалютность (только USD)
Двухфакторная аутентификация / профильные фото
